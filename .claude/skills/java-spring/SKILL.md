# Java · Spring Boot 개발 및 범용 리뷰

## 목적과 적용 원칙

Java·Spring Boot 애플리케이션을 정확하고 유지보수하기 쉽게 구현하고 검토한다. Spring Boot 개발 원칙, DB 공통 기준, 범용 리뷰 절차를 관리한다.

- 사용자 요구사항과 저장소 지침을 우선한다. 기존 구조·기술·버전에 맞춰 변경하고 작업과 무관한 기술 도입이나 구조 개편을 하지 않는다.
- 필수 제약과 권장 관례를 구분한다. 권장 관례와 다르다는 사실만으로 기존 코드를 결함으로 판단하지 않는다.
- 현재 프로젝트가 단일 애플리케이션이면 그 구조 안에서 문제를 해결한다. MSA, 분산 트랜잭션, 메시지 브로커를 기본 해법으로 제안하지 않는다.
- 변경과 관련된 항목만 적용한다. 작은 변경에 전체 점검표나 전면 리팩터링을 강제하지 않는다.
- 확정된 사실, 추정, 미검증 사항을 구분하고 성능 개선은 실제 측정으로 확인한다.

## 작업 모드와 시작 절차

사용자의 요청에 따라 모드를 선택한다.

| 모드 | 수행 범위 | 결과 |
|---|---|---|
| 구현·리팩터링 | 요청 범위의 코드·설정·테스트 변경과 검증 | 변경 이유, 결과, 검증 및 제한 |
| 리뷰 | diff·관련 코드 읽기와 안전한 기존 테스트 실행 | 근거가 있는 발견 사항과 미검증 항목 |

리뷰만 요청받았다면 코드를 수정하지 않는다. 수정까지 요청받았다면 해당 범위에서 진행한다. 이 스킬 자체는 서브에이전트 생성, 커밋·푸시·배포 또는 외부 시스템 변경을 지시하지 않는다.

작업 전에 다음을 확인한다.

1. 저장소 지침, 변경 목적, 기대 동작, 검토 대상 diff 또는 파일.
2. `pom.xml`, `build.gradle` 또는 `build.gradle.kts`, 래퍼, Java 버전, Spring Boot·Hibernate 버전, DB 및 테스트 구성.
3. 컨트롤러 또는 작업 진입점 → 서비스·도메인 → 저장소 → 응답까지 관련 실행 흐름.

누락된 정보는 코드·설정·호출부·테스트에서 먼저 찾는다. 판단을 바꾸는 정보가 끝내 없으면 가정을 명시하거나 필요한 질문을 남긴다. 검토 기준 브랜치나 요구사항을 임의로 확정하지 않는다.

## JPA 작업 연결

엔티티·연관관계·Repository·JPQL, 서비스의 영속 엔티티 변경, 지연 로딩·조회 성능, Hibernate 설정 또는 JPA 테스트를 다루면 [jpa-hibernate](../jpa-hibernate/SKILL.md)를 추가로 읽는다. 웹·설정 등 JPA와 무관한 작업에는 추가 로딩을 요구하지 않는다.

이 문서는 작업 모드·공통 제약·리뷰 심각도·보고 형식의 기준이다. JPA 스킬은 이 절차를 중복 정의하지 않고 영속성 세부 기준을 보완한다. 같은 작업에서 이미 읽은 스킬은 다시 읽을 필요가 없다.

## 참고 예시

핵심 규칙을 코드로 비교할 때는 [Good / Bad 예시](references/good-bad-examples.md)를 읽는다. 생성자 주입, 입력 검증·DTO, 쿼리 바인딩, 트랜잭션 자기 호출·조회/쓰기 구분, 깊은 페이징, 민감 정보 로깅을 다룬다. 해당 작업과 관련된 예시만 적용한다.

## Java 및 프로젝트 구조

- 기존 Maven 또는 Gradle과 래퍼를 사용한다. Spring Boot 의존성 관리 및 starter를 활용하고 필요 없는 버전 재정의나 의존성 추가를 피한다.
- 새 기능은 기능·도메인 중심 패키지 구성을 우선한다. 예: `app.order`, `app.user`. 기존 계층 구조 전체를 요청 없이 재배치하지 않는다.
- 필수 의존성은 생성자로 주입하고 의존성 필드는 `private final`로 선언한다. 기존 프로젝트에서 사용하는 생성자 생성 도구도 존중한다.
- 역할에 맞는 `@Component`, `@Service`, `@Repository`, `@Controller`·`@RestController`를 사용한다.
- null·빈 값·경계값, 예외 처리, 자원 해제, 컬렉션 변경 가능성을 명확하게 다룬다. 예외를 무시하거나 실패를 성공으로 반환하지 않는다.
- 언어 기능은 프로젝트 Java 버전에 맞춘다. 의존성 필드의 불변성 원칙을 JPA 엔티티의 모든 필드나 클래스에 기계적으로 적용하지 않는다.

## 설정과 비밀 관리

- `application.yml` 또는 `application.properties`로 설정을 외부화한다. 새 프로젝트는 계층 표현이 편리한 YAML을 고려하되 기존 형식을 불필요하게 바꾸지 않는다.
- 관련 설정 묶음은 `@ConfigurationProperties`로 타입 안전하게 바인딩하고 필요한 값은 검증한다.
- 환경별 차이는 Spring Profile과 외부 설정으로 관리한다. 기본값·덮어쓰기 우선순위·실제 활성 프로파일을 확인한다.
- 비밀번호, 토큰, 키를 코드나 저장소에 하드코딩하지 않는다. 환경 변수 또는 기존 Vault·AWS Secrets Manager 등 비밀 관리 방식을 따른다.

## 웹 계층과 보안

- 일관된 REST 경로, HTTP 메서드, 상태 코드, 오류 응답을 사용하고 공개 API의 기존 계약을 확인한다.
- API 요청·응답은 DTO로 표현한다. JPA 엔티티를 직접 노출해 영속성 구조, 지연 로딩, 내부 필드가 API에 결합되지 않도록 한다.
- DTO에 `@Valid`, `@NotNull`, `@NotBlank`, `@Size` 등 요구사항에 맞는 Bean Validation을 적용한다. `@Size`만으로 null을 거절한다고 가정하지 않는다.
- Bean Validation은 프로젝트 버전에 맞춘다. Spring Boot 3 이상은 일반적으로 `jakarta.validation`, Boot 2 계열은 `javax.validation`을 사용하므로 import와 의존성을 혼용하지 않는다.
- 전역 예외 처리는 `@RestControllerAdvice` 또는 `@ControllerAdvice`와 `@ExceptionHandler`로 통합한다. 내부 스택·SQL·비밀 값을 응답에 노출하지 않는다.
- 인증·인가가 필요한 애플리케이션에서는 Spring Security와 기존 인증 체계를 사용한다. 인증 여부와 역할뿐 아니라 해당 리소스에 대한 접근 권한도 확인한다.
- 비밀번호를 저장한다면 `PasswordEncoder`와 BCrypt 등 적응형 단방향 해시를 사용한다. 평문 저장이나 복호화 가능한 암호화를 비밀번호 해시 대신 사용하지 않는다.
- SQL·JPQL·네이티브 쿼리는 파라미터 바인딩을 사용한다. JPA를 사용해도 외부 입력으로 쿼리 문자열을 조합하면 안전하지 않다. 정렬 컬럼 등 바인딩할 수 없는 입력은 허용 목록으로 제한한다.
- XSS는 출력되는 HTML·속성·스크립트 등 문맥에 맞는 인코딩으로 방어한다. 허용된 HTML 입력은 검증된 정제 방식으로 처리하며 일괄 문자열 치환으로 해결하지 않는다.
- 외부 호출이 있다면 타임아웃, 실패 처리, 자원 해제, 재시도에 따른 중복 부작용을 검토한다.

## 서비스·도메인 및 트랜잭션

- 컨트롤러는 요청 처리에 집중하고 서비스는 유스케이스 조정과 트랜잭션 경계를 담당한다. 도메인의 불변식·상태 전이 규칙은 도메인 객체에 둘 수 있다. 모든 규칙을 서비스에 몰아넣지 않는다.
- 서비스 빈에 요청별 가변 상태나 공유 영속 엔티티를 보관하지 않는다.
- 함께 성공·실패해야 하는 업무 단위에 `@Transactional`을 적용한다. 단순히 메서드를 작게 나누느라 원자성이 필요한 작업을 여러 트랜잭션으로 쪼개지 않는다.
- 조회 작업에는 `@Transactional(readOnly = true)`를 고려한다. 이는 최적화 힌트이며 모든 쓰기를 차단하는 보안·정합성 장치가 아니다. 실제 동작은 DB·드라이버·JPA 제공자에 따라 확인한다. [Spring Data JPA 트랜잭션 문서](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html)
- readOnly 값으로 데이터소스를 라우팅하는 저장소에서는 readOnly가 최적화 힌트를 넘어 대상 DB를 바꾼다. 이 저장소는 `ReplicationRoutingDataSource`가 readOnly 트랜잭션을 replica로 보낸다(`docs/ARCHITECTURE.md`). 쓰기 경로에 readOnly가 붙지 않았는지, 쓰기 직후 조회가 복제 지연으로 이전 값을 읽지 않는지 함께 확인한다.
- 자기 호출 등 프록시 우회, 예외별 롤백 설정, 예외를 잡는 위치, 전파·격리 수준을 실제 호출 경로에서 확인한다.
- `REQUIRES_NEW` 등 전파 옵션은 독립 커밋의 필요성과 추가 커넥션 사용을 검토한 뒤 선택한다.
- 외부 네트워크 호출과 대량 처리가 트랜잭션을 불필요하게 오래 점유하지 않게 한다. 범위를 줄일 때 업무 정합성이 유지되는지도 확인한다.
- 비동기 실행·스레드 전환 시 트랜잭션과 보안 컨텍스트가 자동으로 이어진다고 가정하지 않는다.

## 페이지와 커서

- 페이지 번호의 기준, 최대 페이지 크기, 정렬 필드 허용 범위를 명시한다.
- 동일한 정렬 값이 있을 때 결과가 흔들리지 않도록 고유한 보조 정렬 키를 포함한다. 예: `createdAt DESC, id DESC`.
- 전체 개수가 필요하면 `Page`, 필요하지 않고 다음 페이지 존재 여부만 필요하면 `Slice` 등을 고려한다.
- 커서 조건은 정렬과 일치시킨다. `id ASC`는 `id > lastId`, `id DESC`는 `id < lastId`이다.
- 복합 정렬은 커서에도 모든 비교 키를 담는다. `createdAt DESC, id DESC`라면 다음 조건을 사용할 수 있다.

```sql
where createdAt < :lastCreatedAt
   or (createdAt = :lastCreatedAt and id < :lastId)
order by createdAt desc, id desc
```

추가 필터와 결합할 때 OR 조건을 괄호로 묶는다. 정렬 값의 null·변경 가능성도 검토한다.

## 인덱스와 커넥션 풀

- 필터, 조인, 정렬, 선택도 및 실행 계획에 근거해 인덱스를 설계한다. `status`나 외래 키가 있다는 이유만으로 인덱스를 일괄 추가하지 않는다.
- 복합 인덱스는 실제 쿼리와 컬럼 순서에 맞춘다. 읽기 개선뿐 아니라 쓰기 비용과 기존 인덱스 중복을 확인한다.
- HikariCP 풀 크기는 DB 연결 한도, 애플리케이션 인스턴스 수, 쿼리 지연, 동시 트랜잭션 수에 맞춰 측정하고 결정한다. 아래 숫자는 원문을 보존한 조정 예시이며 권장 기본값이 아니다.

```properties
# 부하와 DB 연결 예산을 확인한 뒤 조정할 예시
spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.minimum-idle=5
spring.datasource.hikari.connection-timeout=30000
spring.datasource.hikari.validation-timeout=5000
```

- `connection-timeout`은 풀에서 연결을 얻는 대기 제한이며 쿼리 실행 시간 제한이 아니다. `validation-timeout`은 연결 유효성 확인 제한이며 연결 대기 제한보다 작게 설정한다. [HikariCP 설정 문서](https://github.com/brettwooldridge/HikariCP#gear-configuration-knobs-baby)

## 스키마 변경과 마이그레이션

- 운영 스키마 변경은 Flyway 또는 Liquibase 등 버전 관리된 마이그레이션으로 관리한다. Hibernate의 자동 `create`·`update`에 운영 변경을 맡기지 않는다.
- 기존 데이터와 배포 순서가 호환되도록 추가 → 데이터 보정 → 전환 → 제거 순서를 고려한다. 컬럼 삭제나 강한 제약 추가는 별도 호환성·복구 계획을 확인한다.
- 모든 마이그레이션 SQL을 기계적으로 멱등화하지 않는다. Flyway의 버전 마이그레이션은 이력에 따라 한 번 적용되므로 적용된 파일은 수정하지 않고 후속 파일로 변경한다. 반복 실행용 스크립트와 실패 후 재실행 가능한 작업은 별도로 설계한다. [Flyway 버전 마이그레이션 문서](https://documentation.red-gate.com/fd/versioned-migrations-273973333.html)

## 로깅과 검증

- SLF4J와 기존 프로젝트의 로거 선언 방식을 사용한다. 예: `private static final Logger log = LoggerFactory.getLogger(OrderService.class);`.
- 문자열 연결보다 `log.info("주문 처리: {}", orderId)`처럼 파라미터 로깅을 사용한다. 비밀번호·토큰·개인정보나 엔티티 전체를 기록하지 않는다.
- 서비스·도메인 단위 테스트는 JUnit 5를 사용하고 외부 의존성 격리가 필요할 때 Mockito를 활용한다. Java 테스트 검증을 수동 `main()` 실행으로 대체하지 않는다.
- 웹 계층은 `@WebMvcTest`, 전체 컨텍스트 통합은 필요할 때 `@SpringBootTest`를 선택한다. 어노테이션과 import는 프로젝트 버전을 따른다. JPA 계층 테스트 기준은 [jpa-hibernate](../jpa-hibernate/SKILL.md)의 "JPA 검증" 절을 따른다.
- SQL·DB 제약·잠금·격리 수준이 핵심이면 운영과 같은 종류의 DB를 Testcontainers 등으로 검증한다. 실제 대상 DB로 연결됐는지 확인한다.
- mock 기반 단위 테스트로 실제 트랜잭션, 제약 조건, 쿼리 효율, 동시성이 증명됐다고 보고하지 않는다.
- 변경의 중요 동작, 경계값, 실패 경로를 검증한다. 구현을 그대로 복사한 테스트나 영향이 작은 변경의 불필요한 테스트 증가는 피한다.
- 관련 테스트부터 실행하고, 변경 위험 또는 실패 근거가 있을 때 통합 검증으로 확대한다. 실행한 명령·결과·미실행 이유를 남긴다. 운영·공유 DB에 부작용이 있는 테스트를 임의로 실행하지 않는다.

## 리뷰 모드의 판단과 출력

변경 의도와 주요 실행 경로를 확인한 뒤, 위 기준 중 관련 항목을 적용한다. 의심되는 문제는 실제 설정·호출 경로·기존 테스트를 확인해 반례를 찾고, 근거가 확보된 지적만 보고한다.

- 이번 변경이 새로 만들거나 악화한 문제를 우선한다. 기존 문제는 구분한다.
- 같은 원인의 지적은 합친다. 지적 개수를 채우거나 취향 차이를 결함으로 만들지 않는다.
- 근거가 부족한 의심은 확정 결함 대신 질문·미확인 사항으로 분리한다.

| 심각도 | 기준 |
|---|---|
| P0 | 즉시 대응이 필요한 명확한 대규모 장애·심각한 보안 노출·데이터 손실 |
| P1 | 주요 기능 실패·데이터 불일치·권한 우회 등 병합 전 해결이 필요한 문제 |
| P2 | 특정 조건의 오류 또는 근거가 있는 유의미한 성능·유지보수 문제 |
| P3 | 영향이 작지만 구체적인 개선 사항. 선택 항목으로 분리 |

결과는 검토 범위와 주요 결론, 심각도순 발견 사항, 검증 및 제한 순서로 작성한다. 각 발견 사항은 다음 정보를 포함한다.

```text
[P1] 문제를 구체적으로 표현한 제목
- 위치: 파일과 최소한의 관련 줄 번호
- 발생 조건: 입력·상태·호출 순서
- 영향과 근거: 실제 코드 동작, 관련 설정 또는 테스트 결과
- 수정 방향: 필요한 최소 변경
- 검증 방법: 재현 절차 또는 해결 확인 테스트
```

발견 사항이 없으면 “검토 범위에서 확인된 결함 없음”으로 보고한다. 이를 시스템 전체의 안전성 보장이나 테스트 통과로 표현하지 않는다. 직접 실행한 결과와 전달받은 결과를 구분한다.

## 완료 기준

- 구현 모드: 요청된 동작을 구현하고 필요한 검증을 수행했으며 변경 이유·영향·남은 제한을 설명했다.
- 리뷰 모드: 변경의 주요 경로와 관련 위험을 검토하고 지적의 근거·발생 조건·영향을 확인했으며 미검증 사항을 분리했다.
- 두 모드 모두: 적용하지 않은 권장 사항을 이유 없이 결함으로 취급하지 않았고, 사용자 요청 밖의 구조 개편이나 기술 도입을 하지 않았다.

## 사용 예시

```text
/java-spring 회원 정보 수정 API를 구현해줘.
현재 패키지 구조를 유지하고 닉네임 중복 및 동시 요청을 고려해줘.
관련 테스트를 실행하고 검증하지 못한 사항도 알려줘.
```

```text
/java-spring 현재 diff를 리뷰해줘. 코드는 수정하지 마.
요구사항 충족, 트랜잭션 경계, JPA 조회 및 테스트 누락을 확인하고
근거 있는 발견 사항을 심각도순으로 보고해줘.
```

공식 문서는 해당 프로젝트의 버전에 맞춰 확인한다.
