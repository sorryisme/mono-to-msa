## 결론

이 프로젝트에는 **k6 + 부하 테스트 전용 Docker Compose 환경 + 별도 GitHub Actions 워크플로** 구성이 적합하다.

현재도 애플리케이션과 MySQL master/replica를 Compose로 실행할 수 있고 CI에서 MySQL을 기동하는 기반은 있다. 그러나 기존 CI는 애플리케이션을 띄우지 않고 단일 MySQL에서 `./gradlew clean check`만 실행하므로 실제 HTTP 처리량, 세션, 커넥션 풀 포화, master/replica 라우팅은 검증하지 않는다.

부하 테스트를 신뢰할 수 있는 품질 게이트로 사용하려면 다음 세 가지를 먼저 갖춰야 한다.

1. 매 실행 후 폐기할 수 있는 격리된 DB와 재현 가능한 데이터 준비 절차
2. HTTP·JVM·HikariCP·MySQL·replica 지연을 함께 볼 수 있는 관측성
3. 측정값을 왜곡하는 요청/응답 본문 및 Hibernate SQL 로깅을 끄는 부하 테스트 전용 프로파일

### 도입 순서

관측성 전부를 PR smoke의 선행 필수 조건으로 두지 않는다. 아래 순서로 나눈다.

1. 1차(기본): 격리 환경, fixture, readiness, HTTP 판정(threshold), 정리
2. 2차(기본): 주문 경합 시나리오와 DB 사후 검증, JVM·HikariCP 지표
3. 3차(선택 확장): replica·MySQL 상세 지표, nightly/stress/soak

1차·2차까지가 이 프로젝트의 기본 완료 범위다. 3차는 운영 안정성·용량 탐색을 별도로 학습할 때 선택하는 확장 과제이며, 하지 않아도 부하 검증 도입이 미완료인 것은 아니다.

| 스키마 초기화 | `spring.sql.init.mode=always`, `schema.sql`이 테이블을 삭제 후 재생성 | 격리 환경에서만 실행 가능 |

## 도구 선택

### 권장: k6

- 애플리케이션 외부에서 실제 HTTP 요청을 보내므로 Java 빌드와 부하 발생기를 분리할 수 있다.
- VU별 세션 쿠키, 단계별 ramp-up, spike, soak, 일정 도착률 시나리오를 표현할 수 있다.
- 응답 검사와 `p95`, 실패율 등의 threshold 위반을 프로세스 실패로 반환해 CI 게이트로 연결할 수 있다.
- 스크립트가 JavaScript라서 작은 사이드 프로젝트에서도 관리 부담이 비교적 작다.

대안으로 Java DSL과 Gradle 통합을 우선한다면 Gatling을 선택할 수 있다. 다만 현재 프로젝트에는 외부 블랙박스 테스트인 k6가 더 단순하다. 신규 도입 기준으로 JMeter를 우선할 이유는 크지 않다.

## 선행 작업

### 1. 부하 테스트 전용 실행 환경

- [x] `loadtest` Spring profile을 추가한다. (`application-loadtest.yml`)
- [x] 부하 테스트 전용 Compose 파일 또는 명시적 override를 만든다. (`performance/docker-compose.loadtest.yml`)
- [x] 전용 파일에서 고정 `container_name`, 고정 호스트 포트(3306/3307/8080), 개발용 `.env` 의존을 제거한다. (호스트 포트 0개, k6 가 네트워크 내부에서 호출)
- [x] 실행마다 별도 project name과 전용 볼륨을 사용해 개발 환경과 이름·포트·데이터가 충돌하지 않게 한다. (`fmarket-load-<runId>`)
- [x] DB 컨테이너 health check와 애플리케이션 준비 상태 확인을 추가한다. (mysqladmin ping + `readiness.js`)
- [x] master 포트 개방뿐 아니라 replica 초기화·복제 준비 상태를 확인한 후 테스트를 시작한다. 시작 전 source·replica 양쪽 연결 대상을 각각 검증한다. (read_only 0/1, IO/SQL Running)
- [x] 개발·공유·운영 DB 주소에서는 실행할 수 없도록 스크립트에 방어 조건을 둔다. (외부 대상 입력 자체를 받지 않음)
- [x] 테스트 종료 시 컨테이너·볼륨을 정리하되, 정리 대상을 해당 실행의 자원(project name 기준)으로 한정한다. (`trap`, 종료 코드 보존)

`schema.sql`이 기존 테이블을 삭제하므로 공유 DB를 대상으로 실행해서는 안 된다. `depends_on`과 포트 개방만으로 MySQL 초기화·복제·애플리케이션 준비 완료를 보장하지 않으므로 실제 API readiness까지 기다려야 한다.

현재 `docker-compose.yml`은 고정 container_name과 고정 호스트 포트, `.env` 연결을 쓴다. profile 하나만 더해 재사용하면 개발 환경과 충돌하거나 개발용 연결 설정을 그대로 가져올 수 있다.

### 2. 데이터 준비와 정리

- [x] VU 수 이상으로 고유한 테스트 사용자를 미리 생성한다. (`--users`, 기본 100, VU 초과 시 시작 전 중단)
- [x] 로그인 가능한 BCrypt 비밀번호 해시 또는 API 기반 가입 절차를 사용한다. (시드 1명 API 가입 → 해시 복사)
- [x] 상품·상품 옵션·재고를 시나리오별로 재현 가능하게 생성한다. (`performance/sql/fixture.sql`)
- [x] 회원가입과 fixture 생성 시간은 주문·조회 성능 측정 구간에서 제외한다. (k6 실행 전 단계)
- [x] fixture 입력 후 생성한 사용자·상품 데이터가 replica에 반영됐는지 확인한 뒤 부하를 시작한다.
- [x] 시나리오·실행 단위로 데이터를 격리한다. (실행마다 새 볼륨 + `lt-<runId>-` 접두사)
- [x] 테스트 종료 후 주문 수, 재고, 멱등키, 상태 전이를 검증하는 SQL 또는 검증 스크립트를 만든다. 검증은 master의 커밋 결과를 기준으로 한다. (`performance/sql/verify-*.sql`)
- [x] 사후 검증은 쓰기 종료와 진행 중 트랜잭션 정리를 기다린 후 실행한다. (`innodb_trx` 가 비워질 때까지 대기)

현재 `data.sql`의 `dummyUser` 비밀번호는 BCrypt 해시 형식이 아니므로 로그인 부하의 기본 계정으로 사용할 수 없다. 주문 시나리오는 VU별 계정과 세션 쿠키를 유지해야 하며, 서로 다른 정상 주문에는 각각 새로운 UUID 멱등키를 사용해야 한다.

`UserService.login`은 readOnly 트랜잭션이라 replica를 읽는다. 복제 프로세스가 살아 있는 것만으로는 부족하고 fixture가 replica에 도달했는지 확인해야 로그인 단계에서 무작위 실패가 나지 않는다.

### 3. 측정용 로깅 설정

- [x] `loadtest` 프로파일에서 로그 레벨만 낮추지 말고 본문 캐싱·직렬화 경로 자체를 우회한다. (`fmarket.http-log.body-enabled=false`, `MDCLoggingFilter`)
- [x] Hibernate SQL 로그를 WARN 이상으로 낮춘다.
- [x] MDC, 상태 코드, 소요 시간처럼 집계 가능한 지표는 유지한다.
- [x] 로그 제한 전후로 동일한 짧은 부하를 실행해 로깅 오버헤드를 확인한다. (산출물 로그 참고)
- [x] 운영 로깅 정책과 다른 조건으로 측정했다면 그 차이를 결과 보고에 남긴다. (`performance/README.md` "측정 조건")

현재 `MDCLoggingFilter`는 조건 없이 ContentCaching wrapper를 만들고 본문을 문자열로 변환해 `log.info` 인자로 넘긴다(`filter/MDCLoggingFilter.java:35`, `:60`). 요청 본문 캐시에는 64 KiB 상한이 있어 '본문 전체'는 아니지만, 레벨만 WARN으로 올려도 wrapper 생성·인자 평가에 따른 문자열 생성 비용은 그대로 남는다. 높은 부하에서는 애플리케이션 로직보다 본문 복사, 문자열 생성, 콘솔 I/O가 더 크게 측정될 수 있다.

### 4. 관측성

- [x] Spring Boot Actuator와 Micrometer를 도입한다. (2026-09-18, 관리 포트 8081 분리 · Prometheus 스크레이프 엔드포인트)
- [x] HTTP 요청 수·상태·지연 시간을 서버 histogram으로 수집한다. (`http.server.requests` percentiles-histogram, 5ms~10s)
- [x] HikariCP active/idle/pending/timeout을 source와 replica별로 구분한다. (pool 이름 `fmarket-source`/`fmarket-replica`)
- [x] JVM heap, GC pause, 스레드 수, CPU를 수집한다. (actuator 기본 JVM·system binder)
- [ ] k6가 측정한 클라이언트 측 percentile과 서버 histogram 기반 percentile을 구분해 보고한다.

선택 확장 (지연·오류가 실제로 관찰된 다음에 착수한다):

- [ ] 컨테이너 메모리·CPU를 수집한다. (JVM 프로세스 밖이라 별도 수집기 필요)
- [ ] MySQL 커넥션 수, slow query, row lock wait, deadlock을 수집한다.
- [ ] replica 지연과 읽기/쓰기 라우팅을 함께 확인한다.
- [ ] 스크레이프 주기와 보관 방식을 정한다. 지금은 엔드포인트만 있고 시계열을 저장하는 곳이 없다.

HTTP 응답 지연만으로는 애플리케이션 스레드, DB 커넥션 대기, 쿼리, 락, GC 중 어느 지점이 병목인지 구분할 수 없다. HikariCP 크기는 먼저 고정된 조건에서 측정한 다음 DB 연결 예산과 애플리케이션 인스턴스 수에 맞춰 조정한다.

다만 관측성 구축이 병목 분석보다 앞설 필요는 없다. 평소에는 k6 지연·처리량·오류율, 애플리케이션 로그, DB 사후 검증 결과를 남기고, 지연이나 오류가 관찰되면 그때 필요한 JVM·Hikari·쿼리·락 지표부터 확인한다. 이미 있는 Actuator 를 제거할 필요는 없지만 별도 수집기와 장기 보관을 기본 작업으로 두지도 않는다.

## 판정 규칙 (공통)

합격/불합격은 반드시 프로세스 종료 상태로 전달되어야 한다.

- [x] `check()` 실패는 그 자체로 실패 종료 코드를 만들지 않으므로, '기능 check 100%'는 `checks: ['rate==1']` 같은 threshold로 표현한다. (`checks{phase:main}: rate==1`)
- [x] DB 사후 검증 실패도 실행 스크립트와 CI에 실패로 전달한다. (`FAIL` 행 → 종료 코드 1)
- [x] 로그 수집·정리 단계가 원래 실패 종료 코드를 덮어쓰지 않게 한다. (정리는 항상 실행하되 종료 코드는 보존한다)
- [x] 예상된 업무 거절(409)과 실제 실패를 분리한다. 기본 `http_req_failed`는 409를 실패로 집계하므로, 요청별 `responseCallback`과 본문 `code` check 또는 별도 업무 오류 지표를 조합한다. (`lib/http.js` `classify`)
- [x] 예상 거절로 허용하는 `code`는 해당 시나리오에 한정한다. 재고 경합의 `OUT_OF_STOCK`, 중복 키의 `DUPLICATE_REQUEST`, 상태 경합의 `ORDER_STATUS_NOT_CHANGEABLE`를 전역 성공으로 처리하면 잘못된 업무 오류까지 숨는다.
- [x] 최초 로그인과 워밍업 요청은 tag로 구분해 본 측정 threshold에 섞이지 않게 한다. (`phase: setup|login|main`)

## 부하 모델 (공통)

- [x] VU 수는 동시 사용자 수이지 요청률이 아니다. 반복 간 대기, 조회/쓰기 비율, API별 요청량, 워밍업 구간과 본 측정 구간을 각각 정의한다. (각 시나리오 파일 머리말, `performance/README.md` 표)
- [ ] 일정 유입량에서 포화점을 보려면 arrival-rate executor를 별도로 사용하고, 목표/실제 iteration rate·`dropped_iterations`·부하 발생기 자원을 함께 기록한다. (선택 확장, BACKLOG)
- [x] iteration 하나가 여러 HTTP 요청을 보내므로 iteration rate와 RPS를 구분해 표기한다. (요약에 `iterations`·`http_reqs` rate 병기)
- [x] 사용자 수는 arrival-rate 시나리오를 포함해 실제 할당 가능한 최대 VU 안에서 정한다. (fixture 사용자 수 < VU 이면 시작 전 중단)
- [x] k6는 VU iteration마다 cookie jar를 초기화한다. 최초 iteration만 로그인하고 이후 주문을 반복하려면 `noCookiesReset: true` 등으로 세션 유지를 명시한다. 매 iteration 로그인하는 모델은 별도 측정으로 구분한다. (user-flow 는 `noCookiesReset`, 경합 시나리오는 setup 세션을 iteration 마다 jar 에 주입)

## 시나리오와 합격 조건

### 1. Smoke

대상:

- `GET /api/v1/products/category`
- `GET /api/v1/products/{id}`
- `POST /api/v1/products/search`

초기 임시 기준:

- 5 VU, 60초
- 기능 check 100% (`checks: ['rate==1']` threshold로 강제)
- `http_req_failed < 1%`
- `p(95) < 1000ms`

이 값은 용량 목표가 아니라 기동 실패와 심각한 회귀를 잡는 임시 기준이다.

반복 횟수는 합격 조건이 아니다. 단순 실행·기능 확인은 **1회**로 시작한다. 오류나 편차가 의심될 때 추가로 실행하고, 성능 개선 전후를 비교하거나 threshold 를 조정할 때에만 같은 조건에서 2~3회 정도를 탐색적으로 측정한다. 소수 반복만으로 작은 차이의 신뢰성이나 운영 용량을 입증했다고 적지 않는다.

이 반복은 "환경을 다시 만들어 전체를 재실행하는 것"을 말한다. 한 실행 안에서 서로 다른 경쟁 결과를 관찰하는 주문 경합 라운드(`order-race --rounds`)와는 목적이 다르므로 함께 줄이지 않는다.

### 2. 일반 사용자 흐름

```text
로그인 → 상품 검색 → 상품 상세 → 장바구니 추가 → 주문 생성
```

- VU마다 별도의 사용자와 세션 쿠키를 사용하고, iteration 사이에 쿠키가 유지되게 한다.
- 회원가입과 로그인 비밀번호 해싱 비용을 측정 대상에 포함할지 분리해 보고한다.
- 주문마다 고유한 UUID 멱등키를 사용한다.
- 응답 시간뿐 아니라 각 단계의 업무 성공률을 검사한다.
- 정상 처리량 측정이 품절 거절 측정으로 바뀌지 않도록 재고를 충분히 두고 옵션을 분산시킨다. (한정 재고 경합은 아래 3번의 별도 실행으로 분리한다)

### 3. 재고 경합

동일한 상품 옵션에 여러 사용자가 동시에 주문한다. `OrderService.createOrder`의 옵션 ID 정렬과 `InventoryRepository.decreaseQuantity`의 조건부 UPDATE가 실제 MySQL 동시 요청에서도 초과 판매를 막는지 확인한다.

사후 불변식:

```text
성공 주문 수량 합계 <= 초기 재고
최종 재고 >= 0
초기 재고 - 최종 재고 = 성공 주문 수량 합계 - 취소로 복구된 수량 합계
업무적으로 롤백된 요청의 order/order_detail이 남지 않음
```

검증 조건:

- 동시 발사 방식(시작 신호 정렬 여부)과 반복 횟수를 명시한다.
- HTTP timeout은 DB 롤백을 뜻하지 않는다. 응답 유실·timeout 요청은 불변식 판정에서 빼고 별도로 대조한다.
- HTTP 부하만으로 모든 스레드 실행 순서를 입증했다고 표현하지 않는다. 확인하는 것은 결과 불변식이다.

### 4. 멱등성 경합

- 정상 처리량 시나리오: 업무 요청마다 다른 멱등키를 사용한다.
- 중복 요청 시나리오: 동일 사용자·동일 본문·동일 키를 기본으로 두고 여러 VU가 동시에 전송한다. (요청 재전송을 정확히 표현하는 형태)
- 중복 요청에서는 주문과 재고 변경이 정확히 한 번만 발생해야 한다.
- 나머지 요청은 계약된 `DUPLICATE_REQUEST` 응답이어야 하며 예상된 업무 거절을 시스템 실패율과 분리한다.
- 실패 경로 시나리오: '키 저장 후 주문 실패 → 동일 키 재시도'를 추가한다. 재고 부족이나 다중 옵션 중 후순위 옵션 부족을 유도해, 선행 재고 차감·주문·주문 상세·멱등키가 실제 DB에서 함께 커밋되거나 함께 롤백되는지 확인한다.
- 실패한 키의 재시도 계약(재시도 허용 / 영구 거절)을 먼저 정하고 그 계약을 검증한다.
- 서로 다른 사용자의 키 충돌은 별도 계약 검증으로 분리한다. 현재 멱등키는 사용자 구분 없이 전역 UNIQUE이고 응답 재생(replay)은 구현되어 있지 않다.

`IdempotencyAspect`는 `saveAndFlush` 이후 `joinPoint.proceed()`를 호출하고 트랜잭션 advice와의 우선순위를 명시하지 않는다(`aop/IdempotencyAspect.java:25`, `:61`). 키와 주문의 원자성은 정적 코드만으로 확정할 수 없으므로 실행으로 확인한다. 현재 결함이 재현됐다는 뜻은 아니다.

### 5. 취소·확정 경합

동일한 PENDING 주문에 취소와 확정을 동시에 보낸다. 매 라운드마다 새 PENDING 주문을 준비한다. 같은 주문을 계속 재사용하면 첫 전이 이후에는 상태 거절만 반복 측정된다.

사후 불변식:

- 상태 전이 성공은 하나뿐이다.
- 취소 성공 시에만 재고가 정확히 한 번 복구된다.
- 확정 성공 시 재고는 복구되지 않는다.
- deadlock, lock wait timeout, 커넥션 획득 timeout을 별도로 기록한다.

### 6. 단계 부하와 Soak (선택 확장)

아래는 기본 완료 조건이 아니다. 운영 안정성·용량 탐색을 별도 주제로 다룰 때 선택한다.

- nightly: 0 → 20 → 50 VU로 단계 상승, 총 10~15분 (동시 사용자 수 변화이지 일정 요청률이 아니다. 포화점 탐색에는 arrival-rate 시나리오를 따로 둔다)
- stress: 실패율·지연·커넥션 대기가 급격히 증가하는 포화 지점 탐색
- soak: 30~60분 동안 메모리 증가, 커넥션 누수, GC 지연, replica 지연 확인

GitHub 호스팅 러너는 실행 간 성능 편차가 있으므로 PR에서 절대 TPS를 엄격하게 게이트하지 않는다. 용량이나 작은 회귀를 판단할 때는 사양이 고정된 전용 러너 또는 동일한 별도 환경을 사용한다.

## 인덱스·쿼리 확인 대상

- 주문 목록은 `user_id`, `order_date`, 정렬 키를 사용하지만 현재 `order` 테이블에는 PK와 FK만 있다. 대표 데이터로 `EXPLAIN ANALYZE`를 확인한 후 `(user_id, order_date, id)` 등의 인덱스 필요성을 결정한다.

- 문서 상태 구분: 1차·2차 구현은 완료됐고(`performance/`, `scripts/load-test.sh`, 워크플로), 선택 확장은 미착수다. "도입 계획" 이던 부분은 이제 구현된 구성을 설명하는 문서로 읽는다. `performance/README.md` 에 남은 과거 실측 기록은 그 실행 시점의 값이며, 이후 검토에서 재실행해 확인한 결과가 아니다.
- 이 문서는 성능이나 동시성 안전성이 입증됐다고 주장하지 않는다. 확인하는 것은 결과 불변식과 명시된 threshold 통과 여부다.
