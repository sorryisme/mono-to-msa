# 커버리지 제외 범위 축소와 주문 입력 검증 수정

- 일자: 2026-09-14
- 브랜치: `test/coverage-exclude-scope`
- 입력: 대화 지시. JaCoCo 제외 설정이 "제외해도 되는 코드 / 제외하면 안 되는 코드" 기준에 맞는지 점검하고, 점검 결과 1~4번 조치를 한 브랜치로 진행

## 배경: 점검 결과

기존 `jacocoExcludes` 는 `**/entity/**`, `**/dto/**`, `**/config/**`, `**/enums/**`, `**/annotation/**` 를 패키지째 뺐다.
Lombok 생성 코드를 빼려는 의도였지만, 같은 패키지에 있는 **제외하면 안 되는 로직**이 함께 빠져 있었다.

| 빠져 있던 로직 | 성격 |
|---|---|
| `Order.of` — 옵션 판매가 x 수량으로 주문 총액 계산 | 금액 |
| `Product`/`ProductOption` 의 `suspend`·`resume`·`delete` — 삭제 후 전이 거절 | 상태 변경·예외 |
| `CartDetail.changeQuantity` — 1 미만 거절 | 경계 조건 |
| `ReplicationRoutingDataSource` — readOnly 여부로 master/replica 선택 | 트랜잭션 처리 |
| `ProductSearchDto.from` — 본문 null 분기 (전날 500 버그를 고친 지점) | 조건 분기 |
| `OrderCreateDto` 검증·수량 맵, `FieldErrorDto.from` null 처리 | 입력 검증 |

기존 LINE 99.4% / BRANCH 94.1% 는 이 코드를 분모에서 뺀 수치였고, 위 로직을 직접 검증하는 테스트는 없었다.

## 조치

### 1. Lombok 생성 코드는 표식으로 제외 — `lombok.config` (신규)

`lombok.addLombokGeneratedAnnotation = true`. JaCoCo 가 `@lombok.Generated` 메서드를 자동으로 거른다.
리포트에서 `Product` 에 `<init>`, `suspend`, `resume`, `delete`, `isDeleted`, `ensureNotDeleted` 만 남고 getter·builder 가 사라진 것을 확인했다.
record·enum 의 컴파일러 생성 메서드는 JaCoCo 기본 필터가 거른다.

### 2. 제외 목록을 클래스 단위로 축소 — `build.gradle`

```groovy
def jacocoExcludes = [
        '**/FmarketApplication.class',
        '**/annotation/**',
        '**/common/AppConstants.class',
        '**/config/DataSourceConfiguration.class',
        '**/config/WebConfig.class',
]
```

`entity`·`dto`·`enums` 패키지 제외와 `config/**` 전체 제외를 없앴다. `ReplicationRoutingDataSource` 는 다시 집계된다.

### 3. 다시 포함된 로직에 DB 없는 단위 테스트 추가

| 테스트 | 검증 내용 |
|---|---|
| `entity/OrderTest` | 총액 = 판매가 x 수량 합(소수 포함), 상세에 주문 시점 판매가 복사, 요청 수량 없는 옵션은 0, 상태·주문일시 기본값/지정값, 상세→주문 역참조 |
| `entity/ProductStatusTransitionTest` | 상품·옵션 기본 ON_SALE, 판매중지↔재개, 삭제 후 전이 시 예외 + 상태 DELETED 유지, 가격 변경 |
| `entity/CartTest` | 담기/빼기 시 양방향 참조 동기화, 빌더 경유 담기, 목록 불변, 수량 1 허용·0 거절 후 기존 값 유지 |

### 4. 점검 중 발견한 주문 입력 검증 버그 수정 — `OrderCreateDto`

**4-1. 항목 내부 제약이 검사되지 않았다 (점검 과정에서 추가 발견).**
`List<OrderItemRequestDto> orderItems` 에 `@Valid` 가 없어 `OrderItemRequestDto` 의 `@NotNull`·`@Min(1)` 이 동작하지 않았다.
수량 -5 가 통과하면 `InventoryRepository.decreaseQuantity` 의 `quantity >= :quantity` 조건이 참이 되어
`quantity - (-5)` 로 **재고가 늘고**, `Order.of` 총액은 **음수**가 된다.
→ `List<@Valid @NotNull OrderItemRequestDto>` 로 원소 검증을 켰다.

**4-2. 같은 옵션 중복 시 500.**
`toProductQuantityMap` 의 `Collectors.toMap` 이 키 충돌로 `IllegalStateException` 을 던졌다.
수량을 합칠지 한쪽을 버릴지 서버가 추측하지 않도록 **400 으로 거절**하기로 했다.
→ `@AssertTrue isProductOptionIdUnique()` 추가. 응답 필드명은 `productOptionIdUnique`.
API 계약(오류 코드·상태)은 기존 `INVALID_INPUT` 400 그대로이고, `docs/API_RESPONSE.md` 의 발생 상황 설명에만 한 줄 보탰다.

## 하한 재측정

| 시점 | LINE | BRANCH |
|---|---|---|
| 기존 제외 기준 (2026-09-13) | 99.4% | 94.1% |
| 새 제외 기준, 테스트 보강 전 | 93.0% (600/645) | 82.4% (84/102) — 기존 하한 90% 미달 |
| 새 제외 기준, 테스트 보강 후 | **97.1%** (626/645) | **96.1%** (98/102) |

하한은 LINE **95%** 유지, BRANCH **90% → 92%**.
분기가 102개라 1개가 약 1%p 이므로 92% 는 지금보다 분기 4개 정도를 더 놓칠 여유다. 측정치에 딱 붙이지 않는 기존 원칙을 따랐다.

### 남은 미커버 (의도적으로 테스트를 추가하지 않음)

- `entity/User`·`Store`·`ProductReview`·`Inventory` 의 빌더 생성자 대입과 단순 변경 메서드. 분기·계산이 없는 기계적 대입이다.
  이 중 `User.changePassword`·`User.softDelete`·`Store.updateStoreInfo`·`ProductReview.updateReview` 는 **호출처가 없다** → BACKLOG.
- 기존부터 남아 있던 분기: `OrderService` 2개, `GlobalExceptionHandler`·`IdempotencyAspect` 각 1개.

## 테스트 품질 점검 메모

- 외부 DB 의존: `repository/**` 와 `EntityMappingTest` 는 실제 MySQL 을 쓰므로 DB 없이는 `check` 게이트를 통과할 수 없다.
  이번에 추가한 테스트는 모두 DB 없이 돈다. 게이트 자체의 DB 의존은 그대로다 → BACKLOG.
- 실행 순서 의존: `@TestMethodOrder`/`@Order` 사용 없음. 새 테스트 중 스레드 로컬을 건드리는 `ReplicationRoutingDataSourceTest` 는 `@AfterEach` 로 원복한다.
