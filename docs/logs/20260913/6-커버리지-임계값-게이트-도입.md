# 커버리지 임계값 게이트 도입

- 작업일: 2026-09-13
- 브랜치: `chore/jacoco-coverage`
- 범위: `build.gradle`

## 배경

JaCoco 를 처음 넣을 때(`docs/logs/20260913/1-JaCoco-커버리지-도입.md`)는 현재 수치를 모르는
상태에서 하한을 정하면 근거 없는 숫자가 된다고 보아 리포트만 도입하고 게이트는 미뤘다.
이후 `aop` · `utils` · `common` · `controller` 테스트를 차례로 보강해
LINE 80.6% → 99.4%, BRANCH 72.1% → 94.1% 가 됐으므로 이제 하한을 정할 근거가 생겼다.

## 결정한 하한

| 카운터 | 하한 | 현재 |
|---|---|---|
| LINE | **95%** | 99.4% |
| BRANCH | **90%** | 94.1% |

측정치보다 낮게 잡았다. 현재 수치에 딱 붙여 놓으면 사소한 리팩터링마다 빌드가 깨지고,
그러면 개발자가 게이트를 우회하기 시작해 게이트가 있으나 마나 해진다. 여기서 잡으려는 것은
"커버리지가 큰 폭으로 조용히 내려가는 상황"이지 소수점 변동이 아니다.

규칙은 번들(프로젝트 전체) 단위 하나만 뒀다. 클래스·패키지 단위 규칙은 새 클래스를 추가할
때마다 걸려 소음이 커진다.

## 변경 내용

### build.gradle

- 제외 패턴을 `jacocoExcludes` 변수로 뽑아 리포트와 검증이 **같은 대상**을 보게 했다.
  따로 적어 두면 한쪽만 고쳐져 "리포트는 95% 인데 게이트는 다른 숫자를 본다"는 상황이 된다.
- `jacocoTestCoverageVerification` 에 `dependsOn test` 와 위 하한 규칙, 같은 제외 패턴 적용
- `check.dependsOn jacocoTestCoverageVerification`

`scripts/verify-full.sh` 가 `./gradlew clean check` 를 호출하므로 로컬 pre-push hook 과 CI
양쪽에서 그대로 강제된다. 스크립트와 워크플로는 손대지 않았다.

## 검증

게이트가 통과하는 것만으로는 부족하다. 실제로 **실패하기도 하는지** 확인했다.

```
./gradlew clean check
→ BUILD SUCCESSFUL (Task :jacocoTestCoverageVerification 실행됨)

# 하한을 임시로 0.999 로 올려 재실행
→ Task :jacocoTestCoverageVerification FAILED
  Rule violated for bundle fmarket: lines covered ratio is 0.993,
  but expected minimum is 0.999

# 원복 후
./gradlew clean check  → BUILD SUCCESSFUL
```

## 참고

커버리지가 하한 아래로 떨어져 `check` 가 실패하면, 먼저
`build/reports/jacoco/test/html/index.html` 에서 어느 클래스가 내려갔는지 확인한다.
테스트 없이 수치만 맞추려고 제외 패턴을 늘리는 것은 게이트를 무력화하는 일이므로,
제외 대상 추가는 "로직이 없는 코드"라는 기준에 맞을 때만 한다.
