- 작업일: 2026-09-18
- 지시서: `docs/plan/260918-부하-테스트-1-2차.md` (원 계획 `docs/todo/260914-부하-테스트-자동화.md` 의 도입 순서 1차·2차)
- 브랜치: `feature/loadtest-k6-automation` (`chore/actuator-micrometer-metrics` 위에서 분기. 관리 포트·readiness 그룹·Hikari 풀 이름을 그대로 쓴다)
- 범위: 격리 실행 환경, fixture, readiness, k6 시나리오 5개, DB 사후 검증, PR smoke 워크플로, `loadtest` 프로파일. 3차(nightly/stress/soak, MySQL·replica·컨테이너 지표)는 `docs/todo/BACKLOG.md` 로.

## 결론

한 명령(`bash scripts/load-test.sh <scenario>`)으로 기동 → 복제·readiness 확인 → fixture → replica 반영 확인 → k6 → DB 불변식 검증 → 정리가 돌고, 판정이 종료 코드로 나온다.
로컬(Docker Desktop, Windows 11)에서 5개 시나리오를 실제로 실행해 전부 통과했다. 재고 경합에서 초과 판매 0건, 멱등 중복에서 주문 정확히 1건, 취소·확정 경합에서 전이 성공 정확히 1건을 DB 로 확인했다.

## 설계에서 정한 것

- **k6 를 호스트에 설치하지 않는다.** `grafana/k6:1.4.0` 컨테이너가 Compose 네트워크 안에서 `http://java-app:8080` 을 호출한다. 덕분에 호스트 포트를 하나도 열지 않아 개발용 Compose 와 충돌하지 않고, readiness 폴링·시드 가입도 k6 스크립트로 한다.
- **jar 는 호스트에서 만든다.** 기존 `Dockerfile` 은 컨테이너 안에서 Gradle 을 돌려 CI 마다 의존성을 다시 받는다. 부하 테스트는 `./gradlew bootJar` 산출물만 COPY 하는 인라인 Dockerfile 을 쓴다 (계획서의 `performance/Dockerfile` 대신 `dockerfile_inline`. 파일 하나로 끝나서다).
- **사용자 fixture 는 시드 1명의 BCrypt 해시를 복사한다.** 해시에 salt 가 들어 있어 같은 비밀번호로 전원 로그인된다. 회원가입 API 를 N 번 부르는 대신 SQL 한 번이고, BCrypt 비용이 측정 구간에 안 들어간다.
- **fixture ID 는 SQL 출력으로 넘긴다.** `fixture.sql` 의 마지막 SELECT 가 `name<TAB>value` 를 내고 스크립트가 `LT_*` 환경변수로 k6 와 검증 SQL 양쪽에 준다. 앱 스키마에 메타 테이블을 두지 않는다.
- **예상 거절은 시나리오별로만 허용한다.** `classify(res, { OUT_OF_STOCK: 409 })` 처럼 코드→상태 쌍을 넘긴다. 그 밖의 4xx, 5xx, status 0 은 각각 `unexpected_rejects`·`server_errors`·`transport_errors` 카운터로 잡고 전부 `count==0` threshold 다.
- **응답 유실은 불변식에서 뺀다.** 사후 검증은 `DB 주문 수 ∈ [k6 201 수, 201 수 + transport_errors]` 로 판정하고 유실 수를 `INFO` 로 남긴다.

### 멱등키 실패 경로의 재시도 계약 (실측으로 확정)

`IdempotencyAspect` 는 순서를 명시하지 않아 정적으로 확정할 수 없었다. 실측 결과 키가 주문과 같은 트랜잭션에서 롤백됐다(잔존 0건, 재시도가 `DUPLICATE_REQUEST` 가 아니라 `OUT_OF_STOCK` 재현). 트랜잭션 인터셉터가 aspect 바깥에서 실행된다는 뜻이다.
`RETRY_ALLOWED` 를 스크립트 기본 계약으로 고정했다. aspect 순서가 바뀌어 계약이 깨지면 `fail_keys_per_retry_contract` 검증과 `idem_retry_out_of_stock: count==5` threshold 가 실패한다. 코드는 바꾸지 않았다.

### 로깅 우회 전후 (smoke 5 VU × 30s, 같은 환경 연속 2회)

| 조건 | req | avg | med | p95 | p99 | max |
|---|---|---|---|---|---|---|
| 본문 로깅 ON + Hibernate SQL DEBUG (`-Dfmarket.http-log.body-enabled=true -Dlogging.level.org.hibernate.SQL=DEBUG`) | 597 | 5.12ms | 3.10 | 6.21 | 65.5 | 88.8 |
| OFF (`loadtest` 프로파일 기본) | 609 | 4.64ms | 2.93 | 6.17 | 58.0 | 72.6 |

ON 실행의 앱 로그에 `REQUEST_BODY` 598줄, `org.hibernate.SQL` 998줄이 있었고 OFF 실행에는 0줄·compact 610줄이었다(설정이 실제로 적용됨). 5 VU 의 가벼운 읽기 부하에서는 차이가 avg 약 0.5ms 수준이라 잡음과 구분되지 않는다. 우회의 효과는 높은 부하·큰 본문에서 봐야 하며, 이번 측정은 "로깅을 끈 조건에서 측정했다"는 기록이지 오버헤드 수치의 근거는 아니다.

## 실행 중 고친 것

- **`mysql -B` 에서 `\G` 무시**: 복제 확인 루프가 `SHOW REPLICA STATUS\G` 를 배치 모드로 읽어 `Running: Yes` 를 못 찾았다. 상태 조회는 일반 모드(`sql_status`)로 분리했다. 또 실행 중인 bash 스크립트를 편집해 `command not found` 가 났다 — 스크립트가 도는 동안 파일을 건드리지 않는다.
- **setup 의 연속 로그인이 같은 세션을 재사용**: 한 VU 가 여러 계정을 잇달아 로그인하면 jar 에 남은 `JSESSIONID` 가 실려 가 서버가 새 세션을 발급하지 않았다(`login response has no JSESSIONID`). setup 로그인은 요청마다 새 `CookieJar` 를 쓴다.

## 리뷰 반영 (Codex, `docs/review/260918-부하-테스트-자동화-2.md`)

- 로그인 실패가 실행 실패로 이어지지 않던 문제: `login()` 에 check 와 `login_failures` 카운터를 두고 공통 threshold `count==0` 을 추가. user-flow 는 로그인 실패 시 `exec.test.abort()`.
- 워크플로 잔여 정리가 동작하지 않던 문제(`compose ls --format` 템플릿 미지원, `down` 의 변수 요구): Compose 없이 프로젝트 라벨로 컨테이너·볼륨·네트워크·이미지를 직접 제거. `--keep` 실행에 대해 동작 확인.
- 반영 중 낸 회귀: `login_failures` 카운터를 `lib/auth.js` 에 두자 로그인이 없는 smoke 가 그 모듈을 import 하지 않아 k6 가 `no metric name "login_failures" found` 로 시작을 거부했다(PR #11 의 첫 load-test 실행이 잡아냄. 로컬에서는 user-flow 만 재실행하고 smoke 를 빠뜨렸다). 카운터를 모든 시나리오가 import 하는 `lib/http.js` 로 옮기고 smoke·order-race 로 재확인했다.

## 제한과 남은 일

- 로컬 1회 실행값이다. 기준선(같은 환경 3~5회)과 threshold 조정은 BACKLOG.
- CI(`load-test.yml`) 는 작성만 했고 GitHub Actions 에서 실제로 돌려 보지는 않았다. PR 을 올리면 smoke 가 처음 실행된다.
- 동시 발사는 시작 신호를 정렬하지 않는다(k6 VU 순차 기동, 수십 ms 편차). 확인한 것은 결과 불변식이지 스레드 실행 순서가 아니다.
- 서버 지표(JVM·Hikari·MySQL)는 엔드포인트만 있고 스크레이프·보관이 없어 k6 결과와 같은 실행 단위로 대조하지 못한다. 3차.
