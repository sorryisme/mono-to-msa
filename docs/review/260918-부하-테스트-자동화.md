## 판단

방향은 타당하다. k6 + 격리 Compose + 별도 CI는 기존 Java 빌드를 크게 바꾸지 않고 HTTP 경로를 검증하는 합리적인 구성이다. 다만 지금 문서는 도입 방향과 체크리스트이며, 아래 실행·판정 조건을 구체화해야 구현 명세로 사용할 수 있다. 실제 성능이나 동시성 안전성이 입증된 문서는 아니다.

현재 코드로 재확인한 사실:

- 기존 verify CI는 단일 MySQL과 Gradle 검증을 실행하며 별도 HTTP 부하 실행 단계가 없다.
- HttpSession 인증, BCrypt 비밀번호 검사, 로그인에 사용할 수 없는 더미 비밀번호 설명은 맞다.
- 주문 생성은 옵션 ID 순서로 조건부 재고 UPDATE를 실행한다. 취소·확정은 PENDING 상태에 대한 조건부 UPDATE를 사용한다.
- 스키마 DROP/CREATE, 명시적 풀 크기 설정 부재, HTTP 본문 INFO 및 SQL DEBUG 로깅 설명은 대체로 맞다. 요청 본문 캐시는 64 KiB 상한이 있어 '본문 전체'라는 표현은 요청에 대해서는 정확하지 않다.
- 격리 데이터, DB 사후 불변식, 임시 threshold와 실측 기준선의 구분, 인덱스 추가 전 실행 계획 확인은 유지할 만하다.

## 발견 사항

### P1 — CI 합격 조건을 실제 종료 상태에 연결해야 한다

대상: 원본 121~123행, 151~156행, CI 단계.

k6 `check()`는 실패해도 그 자체로 실패 종료 코드를 만들지 않는다. '기능 check 100%'에는 `checks: ['rate==1']` 같은 threshold가 필요하다. DB 사후 검증 실패 역시 실행 스크립트와 CI에 실패로 전달해야 하며, 로그 수집·정리가 원래 실패 코드를 덮어쓰면 안 된다.

기본 `http_req_failed`는 409를 실패로 집계한다. 재고 경합의 `OUT_OF_STOCK`, 중복 키의 `DUPLICATE_REQUEST`, 상태 경합의 `ORDER_STATUS_NOT_CHANGEABLE`는 해당 시나리오에서만 예상 결과로 허용한다. 요청별 responseCallback과 본문 `code` check 또는 별도 업무 오류 지표를 조합해야 한다. 모든 409를 전역 성공으로 처리하면 잘못된 업무 오류까지 숨긴다. 원본은 공통 threshold의 적용 범위가 불명확하다.

근거: [k6 Checks](https://grafana.com/docs/k6/latest/using-k6/checks/), [responseCallback](https://grafana.com/docs/k6/latest/javascript-api/k6-http/set-response-callback/).

조치: 보류.

### P2 — 반복 실행의 세션 유지 방법이 빠져 있다

대상: 원본 62~68행, 133~135행.

k6는 기본적으로 VU iteration마다 cookie jar를 초기화한다. 최초 iteration에서만 로그인하고 이후 주문만 반복한다면 `noCookiesReset: true` 등 명시적 유지 처리가 필요하다. 반대로 매 iteration 로그인은 별도 측정 모델로 구분해야 한다. 최초 로그인과 워밍업 요청을 tag로 구분해 주문 성능 threshold에 섞이지 않게 한다. 사용자 수는 arrival-rate를 포함해 실제 할당 가능한 최대 VU에 맞춘다.

또한 `UserService.login`은 readOnly 트랜잭션으로 replica를 읽는다. fixture 입력 후에는 복제 프로세스가 살아 있는지뿐 아니라 생성한 사용자·상품 데이터가 replica에 반영됐는지도 확인해야 한다.

근거: `service/UserService.java`, [k6 No cookies reset](https://grafana.com/docs/k6/latest/using-k6/k6-options/reference/#no-cookies-reset).

조치: 보류.

### P2 — 부하량과 재고·주문 소비 규칙을 정의해야 한다

대상: 원본 139~173행.

0 → 20 → 50 VU는 동시 사용자 수 변화이지 일정 요청률을 뜻하지 않는다. 반복 간 대기, 조회/쓰기 비율, API별 요청량, 워밍업·본 측정 구간을 정의한다. 일정 유입량에서 포화점을 보려면 arrival-rate executor를 별도로 사용하고 목표/실제 iteration rate, `dropped_iterations`, 부하 발생기 자원도 기록한다. iteration 하나가 여러 HTTP 요청을 보낸다면 iteration rate와 RPS를 구분한다.

일반 주문 부하에 재고 소진 정책이 없으면 초반 주문 생성 후 대부분 품절 거절만 측정한다. 정상 처리량은 충분한 재고·분산 옵션으로, 한정 재고 경합은 별도 실행으로 나눈다. 취소·확정 경합도 매 라운드 새 PENDING 주문이 필요하다. 같은 주문을 계속 재사용하면 첫 전이 이후에는 상태 거절만 반복한다. 동시 발사 방식과 반복 횟수를 명시하고, HTTP 부하만으로 모든 스레드 실행 순서를 입증했다고 표현하지 않는다.

근거: `service/OrderService.java`, [k6 Open and closed models](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).

조치: 보류.

### P2 — 멱등성·재고 사후 검증의 실패 경로를 보강해야 한다

대상: 원본 142~156행.

동일 키 성공 경쟁 외에 '키 저장 후 주문 실패 → 동일 키 재시도'가 필요하다. 현재 `IdempotencyAspect`는 `saveAndFlush` 이후 `joinPoint.proceed()`를 호출하고, 트랜잭션 advice와의 우선순위를 명시하지 않는다. 따라서 키와 주문의 원자성이 보장된다고 정적 코드만으로 확정할 수 없다. 재고 부족이나 다중 옵션 중 후순위 옵션 부족을 유도하여 선행 재고 차감·주문·상세·키의 커밋/롤백을 실제 DB에서 검증하고, 실패한 키의 재시도 계약을 정해야 한다. 현재 결함이 실행으로 재현됐다는 의미는 아니다.

중복 시나리오는 동일 사용자·동일 본문·동일 키를 기본으로 두는 편이 요청 재전송을 정확히 표현한다. 현재 키는 사용자 구분 없이 전역 UNIQUE이고 응답 재생을 구현하지 않는다. 서로 다른 사용자의 키 충돌은 별도 계약 검증이다.

불변식은 실행/시나리오별 격리 데이터와 master의 커밋 결과를 기준으로 검증한다. HTTP timeout은 DB 롤백을 뜻하지 않으므로 '실패한 주문이 남지 않음'은 업무적으로 롤백된 요청에 한정하고 응답 유실·timeout은 별도 대조한다. 쓰기 종료와 진행 중 트랜잭션 정리를 기다린 후 검증한다. 취소가 섞인 경우에는 단순 생성 수량 합계 대신 취소 복구량을 반영한다.

근거: `aop/IdempotencyAspect.java:25`, `aop/IdempotencyAspect.java:61`, `entity/IdempotencyKey.java`, `service/OrderService.java`.

조치: 보류.

### P2 — 로그 출력 중단과 본문 처리 중단을 구분해야 한다

대상: 원본 72~77행.

근거: `filter/MDCLoggingFilter.java:35`, `filter/MDCLoggingFilter.java:60`.

### P2 — Compose profile만으로는 실행 격리가 완성되지 않는다

대상: 원본 52~58행.

현재 Compose에는 고정 container_name과 3306/3307/8080 호스트 포트, `.env` 연결이 있다. profile만 추가하면 개발 환경과 이름·포트가 충돌하거나 기존 연결 설정을 가져올 수 있다. 전용 파일 또는 명시적 override에서 고정 이름·포트·자격증명 의존을 제거하고, 실행별 project name과 전용 볼륨을 사용한다. 정리는 해당 실행 자원으로 제한하고 시작 전에 source/replica 양쪽 연결 대상을 검증한다.

근거: `docker-compose.yml`, `src/main/resources/application.yml`.

## 표현과 도입 순서 제안

- 'Actuator·Micrometer 없음 → 병목 원인 분석 불가'는 과도하다. JFR, 스레드 덤프, MySQL 진단도 가능하므로 '지속적인 지표 수집·상관 분석 체계 부재'가 정확하다.
- 관측성은 필요하지만 모든 수집기를 PR smoke의 선행 필수 조건으로 두지 않아도 된다. 1차는 격리 환경·fixture·readiness·HTTP 판정·정리, 2차는 주문 경합과 DB 검증 및 JVM/Hikari 지표, 3차는 replica·MySQL 상세 지표와 nightly/stress/soak가 현실적이다.
- Actuator 도입만으로 MySQL·컨테이너 지표까지 모두 저장되지는 않는다. 수집·보관 방식과 source/replica pool 식별을 정하고, HTTP percentile의 k6 측정과 서버 histogram 측정을 구분한다. [Spring Boot Metrics](https://docs.spring.io/spring-boot/reference/actuator/metrics.html)
- `5 VU / 60초 / p95 1초` 및 3~5회 반복은 출발점으로 사용할 수 있다. 서비스 SLO나 작은 성능 차이의 통계적 입증으로 해석하지 않는다.

위 제안도 보류 상태이며, 구현이나 실측 검증은 이번 리뷰 범위에 포함하지 않았다.
