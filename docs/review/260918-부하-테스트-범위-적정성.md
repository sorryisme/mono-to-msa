# 부하 테스트 범위 적정성 검토

- 검토일: 2026-09-18
- 수행 주체: Codex
- 대상: `docs/todo/260914-부하-테스트-자동화.md`, `docs/todo/BACKLOG.md`
- 대조: `performance/README.md`, `.github/workflows/load-test.yml`, `docs/TESTING.md`
- 관점: 토이프로젝트에서 기본 부하와 주문 정확성을 검증하는 데 필요한 범위
- 검증: 문서·워크플로 정적 검토. 이번 검토에서 부하 실행이나 성능 측정은 하지 않았다.

## 결론

이미 구현한 짧은 smoke, 사용자 흐름, 주문 경합 검증은 유지할 가치가 있다. 반면 nightly, stress/soak, 전용 러너, 상세 지표 수집·시계열 보관까지 기본 완료 기준으로 두는 것은 현재 목적에 비해 크다. 이 항목들은 운영 안정성·용량 탐색을 별도로 학습할 때 선택하는 확장 과제로 분리하는 것을 권고한다.

## 발견 사항

### P2 — 운영 확장이 기본 완료 조건에 섞여 있다

- 근거: todo 223~253행의 nightly/stress/soak·전용 러너, 265~268행의 nightly 자동화·MySQL 지표·기준선 완료 조건.
- 영향: 기본 부하 검증이 가능해도 운영 자동화와 관측성 확장까지 해야 작업을 완료한 것으로 읽힌다.
- 권고: 기본 완료 조건은 격리 실행, 짧은 HTTP 부하, 명시적인 실패 판정, 쓰기 시나리오의 DB 사후 검증, 결과 기록으로 제한한다. nightly·장시간 soak·포화점 탐색·전용 러너는 선택 과제로 둔다.
- 조치: 반영 (2026-09-18). `docs/todo/260914-부하-테스트-자동화.md` "완료 기준"을 `기본` / `선택 확장` 두 절로 나눴다. 기본은 격리 실행, 짧은 HTTP 부하, 명시적 실패 판정, 쓰기 시나리오 DB 사후 검증, 결과 기록으로 제한했고 모두 충족 상태다. nightly·stress·soak·전용 러너·상세 지표는 선택 확장으로 옮기고 각 절 제목에도 표시했다. 실행 설정(워크플로·스크립트)은 변경하지 않았다.

### P2 — 기준선 반복 실행의 적용 시점이 불명확하다

- 근거: todo 167행, BACKLOG의 기준선 항목, performance README의 기준선 절은 같은 환경에서 3~5회 측정을 요구한다.
- 확인: 검토한 문서에는 전체 테스트를 매번 2~3회 연속 통과해야 한다는 조건이 없다. 현재 워크플로도 선택한 시나리오를 한 번 호출하며 반복 실행 단계나 반복용 matrix가 없다.
- 권고: 단순 실행·기능 확인은 1회로 시작한다. 오류나 변동이 의심될 때 추가 실행하고, 성능 개선 전후를 비교하거나 threshold를 조정할 때에만 같은 조건에서 2~3회 정도를 탐색적으로 측정한다. 횟수 자체를 합격 조건으로 삼지 않는다. 소수 반복만으로 작은 차이의 신뢰성이나 운영 용량을 입증했다고 쓰지 않는다.
- 구분: 전체 환경을 다시 만드는 반복과 한 실행 안의 주문 경합 라운드는 목적이 다르다. 후자는 서로 다른 경쟁 결과를 관찰하려는 것으로 일괄 제거하지 않는다. 현재 order-race 50라운드를 더 늘릴 근거는 이번 검토에서 확인하지 않았다.
- 조치: 반영 (2026-09-18). todo "Smoke" 절과 `performance/README.md` "기준선" 절을 고쳤다. 기본은 1회, 이상 의심 시 추가 실행, 비교·threshold 조정 시에만 2~3회 탐색 측정으로 적고 횟수를 합격 조건에서 뺐다. 전체 재실행 반복과 `order-race --rounds` 를 구분하는 문장을 양쪽에 넣었다. 라운드 수는 변경하지 않았다.

### P3 — 관측성 구축이 병목 분석보다 앞설 수 있다

- 근거: todo 99~111행, BACKLOG의 MySQL exporter·cAdvisor·시계열 보관 확장 항목.
- 권고: 평소에는 k6 지연·처리량·오류율, 앱 로그, DB 사후 검증 결과를 남긴다. 지연이나 오류가 관찰되면 필요한 JVM/Hikari·쿼리·락 지표부터 확인한다. 이미 있는 Actuator를 제거할 필요는 없지만 별도 수집기와 장기 보관을 기본 작업에 추가할 필요도 없다.
- 조치: 반영 (2026-09-18). todo "4. 관측성"에서 미체크 4개(컨테이너 CPU/메모리, MySQL 지표, replica 지연, 스크레이프·보관)를 "선택 확장 — 지연·오류가 실제로 관찰된 다음 착수" 하위 목록으로 내리고, 평소 남길 것(k6 지표·앱 로그·DB 사후 검증)을 명시했다. Actuator 구성은 제거하지 않았다.

### P3 — 최초 검토와 구현 후 상태가 혼재한다

- 근거: todo 상단은 1차·2차 구현 완료지만, 현재 구성 표에는 k6·Actuator 미도입이 남아 있고 마지막 절에는 여전히 도입 계획이라고 적혀 있다. README에는 구현 및 과거 실측 기록이 있다.
- 권고: 최초 점검 당시 상태와 현재 상태를 구분하고, 기본 범위 완료와 선택 확장 미착수를 분리한다. 과거 측정 기록은 이번 검토에서 재실행해 확인한 결과와 구별한다.
- 조치: 반영 (2026-09-18). "현재 구성 점검" 표에 최초 점검일(2026-09-14) 기준임을 명시하고 "점검 이후 변경 (2026-09-18 기준)" 절을 추가했다. 문서 머리말 상태를 `부분 완료` → `기본 범위 완료`로 바꾸고, "현재 검증 범위와 제한"에 문서 상태 구분과 과거 실측 기록의 성격을 적었다.

## 권장 실행 범위

| 항목 | 권장 범위 | 이유 |
|---|---|---|
| smoke | 현재 5 VU·60초, 실행당 1회 | 짧은 HTTP 동작 및 심각한 지연 확인 |
| 일반 사용자 흐름 | 현재 20 VU·60초를 수동 실행하는 수준으로 시작 | 세션과 실제 주문 흐름 확인 |
| 재고·멱등성·취소/확정 경합 | 유지, 관련 로직 변경 시 실행 | 초과 판매·중복 주문·잘못된 재고 복구는 기능 정확성 문제 |
| 데이터 격리·readiness·정리·실패 종료 코드 | 유지 | 테스트 실행과 결과를 신뢰하기 위한 기반 |
| replica 준비·fixture 반영 확인 | 현재 구조에서는 유지 | 현재 로그인·조회 경로가 replica에 의존 |
| PR smoke | 현재 구성 유지 가능, 부담이 확인되면 실행 범위 축소 | 이미 구현되어 있으며 매번 반복할 필요는 없음 |
| nightly·30~60분 soak·전용 러너·전체 지표 수집 | 선택 확장 | 기본 검증보다 운영 안정성 학습에 가까움 |
| 인덱스·쿼리 개선 | 느린 대표 쿼리를 관찰한 뒤 선택 | 부하 테스트 도입 완료와 분리할 성능 개선 작업 |

설정 축소·삭제는 이번 요청의 검토 범위를 넘으므로 수행하지 않았다. 문서 범위 조정 권고만 기록했다.
