## 추천하는 재고 차감 방식

재고를 조회해서 Java에서 검사하기보다 DB가 한 SQL로 검사와 차감을 수행하게 합니다.

UPDATE inventory
SET quantity = quantity - :orderQuantity
WHERE product_option_id = :productOptionId
AND quantity >= :orderQuantity;

처리 결과는 다음과 같이 판단합니다.

- 영향받은 행 1개: 재고 확보 성공
- 영향받은 행 0개: 재고 부족 또는 존재하지 않는 옵션

이 방식은 별도의 비관적 조회 락 없이도 quantity >= 주문수량 검사와 차감이 원자적으로 수행됩니다. 동시에 두 요청이 들어오더라도 DB가 UPDATE 과정에서 필요한 행 잠금을 짧게 획득하므로 초과 판매를 방지할 수 있습니다.

여러 옵션을 주문하는 경우에는 같은 DB 트랜잭션 안에서 옵션 ID 오름차순으로 차감하면 됩니다.

BEGIN

옵션 10 조건부 차감 성공
옵션 20 조건부 차감 성공
옵션 30 조건부 차감 실패
→ 예외 발생
→ 전체 ROLLBACK

COMMIT

따라서 일부 옵션만 차감된 채 남는 문제도 피할 수 있습니다.

## 결제가 추가되면 더 중요한 경계

결제 API 호출은 DB 트랜잭션 안에 포함하면 안 됩니다.

트랜잭션 시작
재고 비관적 락 획득
외부 결제 API 호출 — 수 초 대기
결제 응답
트랜잭션 커밋 및 락 해제

이 구조는 외부 결제가 느려지는 동안 재고 락까지 계속 유지합니다. 결제 장애가 DB 커넥션 고갈과 주문 적체로 전파될 수도 있습니다.

결제를 고려하면 주문을 다음 상태로 관리하는 것이 좋습니다.

재고 확보
↓
PAYMENT_PENDING
↓
결제 성공 → PAID 또는 COMPLETED
결제 실패/만료 → CANCELLED + 재고 복구

권장 흐름은 다음과 같습니다.

### 1. 주문 및 재고 예약 트랜잭션

BEGIN

멱등성 키 확인
조건부 재고 차감
주문 상태를 PAYMENT_PENDING으로 저장

COMMIT

여기서 차감한 재고는 실제 판매 완료라기보다 일정 시간 동안의 재고 예약으로 해석할 수 있습니다.

### 2. 트랜잭션 밖에서 결제 요청

PG 결제 API 호출

결제 요청에는 주문 ID 기반의 멱등성 키를 사용해야 합니다. 네트워크 타임아웃 때문에 응답을 못 받았더라도 같은 결제가 중복 실행되지 않아야 합니다.

### 3. 결제 결과 반영

결제 성공:

UPDATE orders
SET status = 'PAID'
WHERE id = :orderId
AND status = 'PAYMENT_PENDING';

결제 실패 또는 예약 만료:

UPDATE orders
SET status = 'CANCELLED'
WHERE id = :orderId
AND status = 'PAYMENT_PENDING';

상태 변경에 성공한 요청만 재고를 복구해야 합니다. 이렇게 해야 결제 실패 처리, 사용자 취소, 만료 배치가 동시에 실행되어도 재고가 두 번 복구되지 않습니다.

## 현재 코드에 적용한다면

현재 구현에서 저는 다음 방향을 추천합니다.

1. 재고 옵션당 한 행만 존재하도록 UNIQUE(product_option_id)를 추가합니다.
2. findAllByProductOptionIdInForUpdate() 대신 조건부 차감 UPDATE를 만듭니다.
3. 여러 옵션은 ID 오름차순으로 차감하여 데드락 가능성을 줄입니다.
4. 주문 생성 시 상태를 PAYMENT_PENDING 또는 STOCK_RESERVED로 저장합니다.
5. DB 트랜잭션이 끝난 후 결제를 요청합니다.
6. 결제 성공·실패·취소는 조건부 상태 UPDATE로 한 번만 처리합니다.
7. 일정 시간 결제가 끝나지 않은 주문을 만료시키고 재고를 복구합니다.
8. 결제 결과 유실에 대비해 PG 조회 API와 대사하는 배치 또는 이벤트 재처리를 둡니다.

현재 PENDING → COMPLETED/CANCELLED만으로도 구현할 수는 있지만, PENDING이 “주문 생성됨”, “재고 예약됨”, “결제 진행 중” 중 무엇인지 모호해질 수 있습니다. 결제를 붙일 계획이라면 상태 의미를 분리하는 편이 좋습니다.

## 비관적 락을 유지할 만한 경우

반대로 다음과 같은 조건이라면 비관적 락을 선택할 근거가 충분합니다.

- 한정판이나 선착순 상품처럼 특정 재고 행에 요청이 집중된다.
- 충돌이 매우 잦아 낙관적 락 재시도가 대부분 실패한다.
- 한 주문의 재고 검증 로직이 복잡해 단순 조건부 UPDATE로 표현하기 어렵다.
- 트랜잭션이 짧고 DB 처리량보다 정확한 순차 처리가 더 중요하다.
- 락 대기 시간, 데드락, 타임아웃을 운영 환경에서 관찰하고 있다.

다만 한정판처럼 트래픽이 아주 큰 경우에도 비관적 락 하나로 버티려 하기보다 대기열, 재고 예약, 트래픽 제한 등을 함께 고려해야 합니다.

결론적으로 이 프로젝트에서는 이렇게 정리할 수 있습니다.

> 일반 상품 재고는 조건부 원자적 UPDATE로 처리하고, 주문 상태 전이 역시 조건부 UPDATE로 중복 처리를 방지한다. 결제는 DB 트랜잭션 밖에서 수행하며, 결제 대기 동안에는 재고를 예약 상태로 관리한다. 비관적 락은 충돌 빈도와 업무 복잡도가 실제로 높
> 다는 측정 결과가 있을 때 선택한다.

이 방향이 정합성은 유지하면서도 결제 추가와 트래픽 증가에 더 자연스럽게 확장됩니다.
