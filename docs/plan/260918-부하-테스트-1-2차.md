## 목표

한 명령으로 격리 환경 기동 → 데이터 준비 → k6 부하 실행 → DB 업무 불변식 검증 → 정리가 수행되고, 합격/불합격이 프로세스 종료 코드로 전달된다. PR 에서는 smoke 만 자동 실행한다.

## 1. 격리 실행 환경

- `performance/docker-compose.loadtest.yml` 신규. 서비스: `db-master`, `db-replica`, `java-app`, `k6`(`grafana/k6`, `profiles: [tool]`).
  - `container_name`, 호스트 포트, `env_file` 을 쓰지 않는다. 자격증명은 실행 스크립트가 매번 `openssl rand` 로 만들어 환경변수로 넘긴다.
  - DB 는 기존 `docker-init/`, `docker-init/mysql-config/` 를 그대로 마운트한다. MySQL 두 서비스에 `healthcheck`(mysqladmin ping) 를 두고 `java-app` 은 `service_healthy` 조건으로 기다린다.
  - k6 는 같은 Compose 네트워크 안에서 `http://java-app:8080` 을 때린다. 호스트에 k6 설치가 필요 없다.
- `performance/Dockerfile`: 런타임 전용 이미지. 스크립트가 호스트에서 `./gradlew bootJar -x test` 로 만든 jar 를 COPY 한다(CI 마다 컨테이너 안에서 Gradle 을 다시 돌리지 않기 위함).
- `scripts/load-test.sh` 한 명령:
  1. 실행 ID(`runId`) 생성, Compose 프로젝트명 `fmarket-load-<runId>`
  2. jar 빌드
  3. `compose up -d db-master db-replica java-app`
  4. replica 복제 상태 확인 (`Replica_IO_Running`/`Replica_SQL_Running` 모두 Yes)
  5. 앱 readiness 확인: k6 로 `http://java-app:8081/actuator/health/readiness` 를 폴링, 자체 타임아웃 180초
  6. fixture: 시드 사용자 1명을 회원가입 API 로 만들고, 그 BCrypt 해시를 재사용해 SQL 로 사용자 N 명 복제. 상품·옵션·재고 fixture SQL 실행
  7. replica 반영 확인 (사용자 수·옵션 수가 replica 에서 동일해질 때까지 폴링)
  8. `compose run --rm k6 run <scenario>.js` (요약 JSON 은 `build/loadtest/<runId>/` 로)
  9. 시나리오별 사후 검증 SQL 실행 (master 기준, `FAIL` 행이 있으면 실패)
  10. `trap` 으로 앱 로그 수집 후 `compose -p <proj> down -v`. 정리 대상은 이 프로젝트명으로 한정하고 원래 종료 코드를 보존한다.
- 방어 조건: 스크립트는 외부 DB 주소나 대상 URL 을 입력받지 않는다. 대상은 항상 자체 생성한 Compose 프로젝트 내부다.

## 2. 앱 측 변경

- `src/main/resources/application-loadtest.yml`: `logging.level.org.hibernate.SQL: WARN`, `spring.jpa.properties.hibernate.format_sql: false`, `fmarket.http-log.body-enabled: false`.
- `MDCLoggingFilter`: `fmarket.http-log.body-enabled` 가 false 이면 ContentCaching wrapper 를 만들지 않고 `method uri status elapsedMs` 한 줄만 INFO 로 남긴다. MDC(request_UUID, uri, method) 는 유지한다. 단위 테스트를 추가해 커버리지 게이트를 유지한다.

## 3. 데이터 준비 (`performance/sql/`)

- `fixture.sql`: 실행 파라미터(사용자 수, 옵션 수, 재고)를 세션 변수로 받는다.
  - 사용자: 시드 계정의 `password`/`salt` 를 복사해 `lt-<runId>-<n>` 계정 N 명 생성 (`INSERT ... SELECT`). 모두 같은 비밀번호로 로그인 가능.
  - 흐름용 상품 1개 + 옵션 20개, 옵션당 재고 1,000,000 (정상 처리량 측정이 품절 측정으로 바뀌지 않게).
  - 경합용 상품 1개 + 옵션 1개, 재고는 파라미터(기본 50).
  - 멱등 실패 경로용 옵션 2개: 선행 옵션 재고 충분, 후순위 옵션 재고 0.
  - 취소·확정용 옵션 1개, 재고 1,000,000.
  - 생성한 옵션 ID 들은 `loadtest_meta`(이름, 값) 테이블에 기록해 k6 와 검증 SQL 이 같은 값을 읽는다.
- `verify-<scenario>.sql`: `check_name`, `PASS|FAIL`, `detail` 3 컬럼을 출력한다.

## 4. k6 시나리오 (`performance/k6/`)

- `lib/config.js`: BASE_URL, MGMT_URL, RUN_ID, 사용자 비밀번호, 메타 값 읽기(환경변수 주입).
- `lib/auth.js`: VU 별 계정 로그인, 세션 쿠키 유지(`noCookiesReset: true`), `phase:login` 태그.
- `lib/checks.js`: 응답 봉투 검사, 시나리오가 허용한 `code` 만 예상 거절로 분류하는 `responseCallback`/카운터.
- `lib/thresholds.js`: 공통 threshold 생성기 — `checks: rate==1`(setup/login/warmup 태그 제외), `server_errors: count==0`, `timeouts: count==0`.
- `readiness.js`: readiness 200/UP 까지 폴링, 데드라인 초과 시 실패 종료.
- `smoke.js`: 5 VU · 60초, 카테고리·상세·검색. `p(95)<1000ms`, `http_req_failed<1%`.
- `user-flow.js`: 로그인 → 검색 → 상세 → 장바구니 → 주문(고유 UUID, 옵션 분산). VU 당 전용 계정, 최초 iteration 만 로그인, iteration 사이 sleep.
- `order-contention.js`: 한정 재고 옵션에 N VU 가 동시 주문. 허용 code `OUT_OF_STOCK` 만. 사후 SQL 불변식: 성공 수량 합 ≤ 초기 재고, 최종 재고 ≥ 0, 초기−최종 = 성공 수량 합, 롤백 요청의 주문 없음.
- `idempotency.js`:
  - (a) 중복: 동일 사용자·본문·키를 M VU 가 동시에 K 번 전송. 키는 `<runId8>-0000-4000-8000-<12자리>` 형식으로 만들어 SQL 에서 prefix 로 찾는다. 키당 201 정확히 1건, 나머지 `DUPLICATE_REQUEST`. 사후: 키 수 = K, 주문 수 = K.
  - (b) 실패 경로: 옵션 2개(후순위 품절) 주문 → `OUT_OF_STOCK` → 동일 키 재시도. 하드 불변식: 해당 사용자 주문 0건, 선행 옵션 재고 원복. 재시도 응답(재시도 허용 / `DUPLICATE_REQUEST`)은 첫 실행에서 실측해 계약으로 문서에 확정한 뒤 threshold 로 고정한다.
- `order-race.js`: setup 에서 R 개 PENDING 주문 생성, `cancel`/`confirm` 두 executor 가 같은 인덱스 순서로 동시 전송. 주문당 200 정확히 1건 + `ORDER_STATUS_NOT_CHANGEABLE` 1건. 사후 SQL: 상태 ∈ {CANCELLED, COMPLETED}, 최종 재고 = 초기 − COMPLETED 수량 합.

## 5. CI (`.github/workflows/load-test.yml`)

- `pull_request` → smoke job (`scripts/load-test.sh smoke`).
- `workflow_dispatch` 입력: `scenario`(choice), `vus`, `duration`. 외부 URL 입력은 받지 않는다.
- 정리는 `if: always()`. k6 요약·앱 로그·검증 결과를 아티팩트로 업로드한다.
- nightly 스케줄, stress/soak, 전용 러너는 BACKLOG.

## 6. 검증

- 로컬(Docker Desktop)에서 5개 시나리오를 실제 실행하고 결과를 산출물 로그에 남긴다.
- `./gradlew test` 로 필터 변경을 검증한다.
- 로그 우회 전후 smoke 를 각각 실행해 차이를 기록한다.
